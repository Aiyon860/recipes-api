# ADR 0001: Recipe Collection — Data Model and Stack Decisions

- Status: Accepted
- Date: 2026-08-09

## Context

Practice API to learn the modern Python web stack — FastAPI, Pydantic v2,
SQLAlchemy 2.0, Alembic — on SQLite. Must fit in one day. Goal: a domain that
forces real modeling decisions (relationships, cascades, association tables,
nested validation) without defaulting to boring e-commerce CRUD
(users / products / orders). Chosen domain: **recipe collection**.

### Scope guardrails (from the grilling session)

- One-day budget: 3-5 tables, ~9 endpoints, no auth, no soft-delete.
- SQLite for simplicity; no Postgres-specific features.
- User preference: `pip` + venv, not `uv`.

## Decision 1 — Ingredients: child table (not JSON, not catalog M2M)

| Option | Cost | Lesson | Verdict |
|--------|------|--------|---------|
| JSON column + Pydantic | Low | Pydantic nesting | rejected — no SQL queryability |
| **Child table `ingredients`** | Medium | `1:N` + cascade | **chosen** |
| Catalog + M2M association | High | fullest modeling | rejected — 1.5x work, breaks day budget |

Consequences:
- `ingredients.recipe_id` FK → `recipes.id`, `ondelete="CASCADE"`.
- `ingredients.position` gives stable ordering; relationship uses `order_by`.
- Quantity = `Numeric(10,3)` → Python `Decimal` (no float drift on `0.5 tbsp`).
- Unit = free-text `String(50)` — a curated unit enum was rejected (enum
  maintenance, client friction, not worth it for practice).

## Decision 2 — Tags: pure M2M association table

The one place to teach a real many-to-many. `recipe_tags` join table maps
`recipes` ↔ `tags`, `ON DELETE CASCADE` both sides.

Consequences:
- `tags.name` unique (`String(50)`, indexed).
- `GET /tags` returns per-tag recipe counts (aggregation practice).
- Recipe creation resolves tag names → existing tags, creating missing ones.

## Decision 3 — Instructions: ordered JSON steps

`JSON` column on `recipes`, validated at the API boundary by a Pydantic `Step`
model (`number`, `text`). Not SQL-queryable — acceptable, nobody queries
"recipes whose step 3 contains X". Saves a second child table while still
exercising nested-list validation in Pydantic.

## Decision 4 — Sync SQLAlchemy 2.0 typed style + Alembic

- `Mapped[]` / `mapped_column()` typed mappings; sync `Session` injected through
  a `get_db()` yield dependency. Async (`aiosqlite`) rejected: more moving parts,
  same modeling lessons, risks the day budget.
- Alembic autogenerated initial migration; `create_all` rejected (teaches nothing
  about migrations — the real-world norm).
- Config via `pydantic-settings` (env prefix `RECIPES_`, `lru_cache`).

## Non-decisions (explicitly out of scope)

- No auth — public read/write API; keeps focus on modeling.
- No stats endpoint, no soft-delete, no ingredient unit conversion — all deferred
  stretch goals.
- No `__init__`-package boilerplate beyond `src/recipes_api/`.

## Consequences

- ~9 endpoints: recipe CRUD, list with pagination + tag filter + name search,
  tag list + create.
- pytest + httpx `TestClient` suite against a temporary SQLite DB: CRUD, cascade
  delete, tag filter, search, pagination, validation errors.
- Docs produced as we build: this ADR, `docs/glossary.md`, `README.md`,
  `TODO.md` (guided build plan).
